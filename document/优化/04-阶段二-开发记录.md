## 0. 这一阶段加了什么

一句话：**给主循环装了一个第三方裁判，在四个偏移高发的时刻各看一眼"你现在走的路还对不对"。**

关键在"第三方"三个字。反思不在主 agent 的上下文里，它是一次**独立的旁路 LLM 调用**：
独立 system prompt、独立 client、独立上下文。所以它对主循环的 token 预算**零成本**——
主 agent 看不到它，只有在判定为偏移时才收到一条注入的 system reminder。

```
主循环（回合 N）                     裁判（旁路 goroutine）
─────────────────────────────────    ──────────────────────────────
工具结果落盘
  ↓
ObserveTools → 命中四事件之一
  ↓
Fire(trigger, conv)  ─────────────→  快照 goal + trace（同步，避免与主循环抢 conv）
  ↓  不等待                            ↓
（继续回合 N 的收尾）                  judge(systemPrompt, goal+trace)
                                       ↓
回合 N+1 开头                          on_track? ──┐
  ↓                                                   │
Consume(conv)  ←────── 1 深缓冲（只留最新判定）─────────┘
  ├─ 就绪 → 处置链（Yes 清零 / No 重申 / 连续 No×3 重规划）
  └─ 超时 5s → 丢弃本次判定，K 窗口不计
```

## 1. 对任务书的修订（面试要主动讲这一条）

任务书 §1 里有两条我做了修订，实现里都带着理由注释：

| 条目 | 任务书原文 | 实现 | 理由 |
|---|---|---|---|
| 2.1 | 反思"采 3 次投票防抖" | **每事件 1 次调用，K=3 滑动窗口承担防抖** | 字面双层防抖 = 每偏移要 9 个 No 才中断，处置链钝化、成本 ×3，简历那个 32%→11% 的数字出不来 |
| 2.2 | 周期性检查兜底（可配置关闭） | 保留 `reflection.periodic`，**默认 false** | 事件驱动才是卖点；周期检查稀释叙事且制造无谓 token |

"主动讲"的话术：**"任务书最初写的是 3 次投票，我把投票折叠进滑动窗口了——
如果每事件真跑 3 次，一个偏移要 9 个 No 判定才中断，处置链会钝化成
'看到了但来不及拦'。我把 3 次投票理解成'连续 3 个不同的事件都判 No'，
这在信息量上等价，成本降到 1/9。"**

## 2. 逐文件详解

### 2.1 `internal/agent/reflection.go`（新增，~880 行）

#### 2.1.1 判定值与"无效"这个第三态

```go
type ReflectionVerdict struct {
	OnTrack   bool
	Deviation string
	Valid     bool   // ← 第三态
	...
}
```

`bool` 只有两个值，但裁判的实际状态有三种：**Yes / No / 判定无效**。用 `bool` 会把
"裁判返回了一段垃圾"折叠成 No——于是**裁判一坏，系统就变成持续告警**；
如果折叠成 Yes，情况更糟：**裁判一坏，目标偏移检测被静默关掉，而外观看起来完全正常**。

所以解析失败一律 `Valid=false`，且**不进 K 窗口**。这是 K=3 能真正防抖的前提：
K 窗口计的是"agent 连续偏了 3 次"，不是"裁判连续吐了 3 次字"。

`parseReflectionVerdict` 里三个拒绝条件值得单独说：

1. `on_track` 字段缺失 → 无效。用 `*bool` 指针区分"缺失"和"false"，
   否则 `{}` 会被读成一次自信的 No。
2. **No 但没写 deviation** → 无效。注入的 reminder 会变成"你偏了，但没说偏哪儿"，
   这种指令主 agent 无法执行，只会白白消耗一次回合。
3. JSON 截断 / 夹杂散文 → 无效（`extractJSON` 做容错抽取，失败即无效）。

#### 2.1.2 latest-wins：**按序号，不按到达顺序**

这是本阶段最容易写错、也最值得讲的一处。

```go
// "最新" = 最大的 fire 序号，不是"最后到达的"
case buffered := <-r.pending:
    if buffered.seq > res.seq {
        // 缓冲里已经是更新的判定 → 放回去，丢弃这条迟到的旧判定
        return
    }
    // 否则这条更新，占位
```

**为什么不能按到达顺序？** 裁判调用是并发 goroutine，完成顺序和触发顺序无关。
实践中**旧轨迹的判定更可能是最后落地的那条**（它触发得早，排队排得久）。

如果按到达顺序顶掉，主循环就会拿到一条**关于它已经走过的轨迹的判定**——
不仅白费一次 K 窗口计数，还可能基于过时的判断发起一次"重规划"。

`Consume` 里额外再做一次 `res.seq < target` 校验：那是判定真正进入对话的地方，
不能只信任缓冲区。

`abandonedSeq` 处理另一条过期路径：主循环等超时后已经把该序号划掉，
之后迟到的同序号结果必须丢弃，不能乱序生效。

单测 `TestLatestVerdictOverwritesOlder` 专门构造"旧判定最后落地"这个场景来钉死它。

#### 2.1.3 Fire 的空输入判断踩了坑（race detector 抓到的）

第一版写的是：

```go
input = buildReflectionPrompt(goal, trace)
if input == "" { return }   // ← 永远不成立
```

`buildReflectionPrompt` 返回的是带 `## Task goal` / `## Recent trajectory` 骨架的字符串，
**永远非空**。所以这个守卫形同虚设，空对话也会白发一次 LLM 调用。

`-race` 跑出来的报告指向的是我测试脚手架的一个竞态，但顺着查下去发现了这个真 bug。
修正后的守卫判的是 **goal**：

```go
if goal == "" { return }
```

（空 trace 但有 goal 是另一回事，仍然要调用——"agent 还没动手"本身是个合法的判定输入。）

**这条记在踩坑里，因为它代表一类错误**：守卫写在错误的层级。
"这次调用有没有意义"要在**组装之前**判，而不是组装之后再问"拼出来的东西空不空"。

#### 2.1.4 目标提取：跳过 system-reminder 和 autoMemory

```go
if strings.HasPrefix(c, "<system-reminder>") { continue }
if strings.HasPrefix(c, "# autoMemory") || strings.HasPrefix(c, "# tencoderMd") { continue }
```

Tencoder 自己会往对话里注入大量 user 角色消息：plan-mode reminder、deferred tool 列表、
task notification、auto memory 头。如果随手抓到一条当"任务目标"，
裁判就会把"可用工具清单"当成目标，然后对着它判偏移——**凭空制造误报**。

`captureGoal` 还有一条：**目标一经捕获就固定**（`goalCaptured`）。
用户中途改主意时，不能让"目标"跟着漂移——否则裁判在追一个移动的靶子。

#### 2.1.5 轨迹摘要：一行一步，全文截断

```go
call: EditFile internal/auth/login.go
result[ok]: applied 3 edits
assistant: Now let me check the test
```

裁判要的是**路径的形状**（看了哪个文件 → 改了哪个文件 → 测试结果如何），
不是 2000 行 diff 的内容。所以每个动作压成一行，正文截到 160~200 字符，
整体再按 `TraceMaxBytes`（8KB）硬截。

`describeArgs` 只保留 `file_path`/`command`/`query` 这几个能标识目标的参数——
`WriteFile` 的完整 arguments 可能有几 KB。

#### 2.1.6 并发安全与"不碰 conv"

**Fire 里的快照是同步做的**（`captureGoal`/`buildTrace` 在主循环 goroutine 上完成），
只有 LLM 调用进 goroutine。

这一点很重要：`conv.GetMessages()` 在主循环 goroutine 之外调用会和主循环的
`append` 撞车。现有的 extractor 有同样的隐患（它在 `OnLoopComplete` 里读 conv），
但那是主循环**结束后**才读，时序不同。这里是回合中途，必须先快照再异步。

同理 `NotifyAnomalyCallback` 传 `nil` conv——异常回调那条路正在重写 conv
（强制压缩会 `TruncateTo` + `AppendMessages`），那时候去读它是自找麻烦。

#### 2.1.7 统计埋点

`ReflectionStats` 覆盖验收标准 2 和 3 需要的全部字段：
`Calls` / `Triggers`（四事件归因）/ `OnTrack` / `Drift` / `Invalid` / `Timeouts` /
`Overwrites` / `Reminders` / `Replans` / `InputTokens` / `OutputTokens`。

`Stats()` 返回深拷贝（`Triggers` map 也复制）——
单测 `TestStatsSnapshotIsIndependentCopy` 钉死了这一点：外部拿到统计后改 map，
不应该污染 Reflector 内部状态。

### 2.2 `internal/agent/agent.go`（改，接线）

**四处改动，每处都挑了位置：**

| 事件 | 挂点 | 为什么挂这儿 |
|---|---|---|
| 消费判定 | 回合循环开头，`a.Client.Stream` **之前** | 请求发出后再注入 system reminder 是不可见的 |
| 工具事件 | `AddToolResultsMessage` 之后 | 此刻轨迹已完整，且主循环接下来还有一整个回合的活给裁判当 head start |
| 异常回调 | `handleStreamError` 的两条 retry 路径 | 限流重试 / 上下文超长强制压缩重试 |
| max_tokens | escalation + recovery 两处 `continue` 之前 | 输出被截断后 agent 正在"续写"，最容易跑偏 |

```go
// 回合开头
a.Reflector.Consume(conv)
```

```go
// AddToolResultsMessage 之后
if a.Reflector.Enabled() {
    var toolNames []string
    hadError := false
    for _, r := range results {
        toolNames = append(toolNames, r.toolName)
        if r.isError { hadError = true }
    }
    if trigger := a.Reflector.ObserveTools(toolNames, hadError); trigger != "" {
        a.Reflector.Fire(trigger, conv)
    } else if a.Reflector.NotifyPeriodic(iteration) {
        a.Reflector.Fire(TriggerPeriodic, conv)
    }
}
```

注意 `else if`：一个回合**最多一次**裁判调用。事件触发的优先级高于周期兜底，
命中事件就不再补周期检查——这是成本上限。

**周期兜底用 `else if` 而不是独立分支**：若两者都触发就会在同一回合烧两次调用，
而周期检查本身只是兜底，优先级明显更低。

#### 四个事件的检测逻辑（`ObserveTools`）

```go
var readOnlyTools = map[string]bool{"ReadFile": true, "Glob": true, "Grep": true, "ToolSearch": true}
var writeTools    = map[string]bool{"EditFile": true, "WriteFile": true}
```

固定列表而不是 per-tool 元数据：只需知道"刚去看东西"还是"刚改东西"，
新增一个只读工具就是加一行、便于 review 的改动。

优先级：

```go
switch {
case hadError:                       trigger = TriggerToolFailure
case writeSucceeded && !writeSeen:   localization 或 patch
}
```

**一个回合只产出一个触发**。写失败同时是"补丁生成"和"测试失败"时归给后者——
一次失败的写，比"补丁存在"携带更多关于路径走歪了的信号。

**`writeSeenAfterRun` 保证定位完成只触发一次**。否则一个 20 次编辑的长序列，
第 2 次编辑之后每次编辑都会烧一次裁判调用。

**刻意不推断 Bash 语义**。任务书自己的规则就是"按 isError 判，不猜命令语义"。
Bash 输出千变万化，猜错会在每次 `grep` 后都触发裁判。

### 2.3 `internal/config/config.go`（改，配置项）

```go
type ReflectionConfig struct {
	Enabled                  *bool `yaml:"enabled"`                   // 默认 true
	Periodic                 *bool `yaml:"periodic"`                  // 默认 false
	PeriodicEvery            int   `yaml:"periodic_every"`
	MaxWaitMs                int   `yaml:"max_wait_ms"`               // 默认 5000
	DriftThreshold           int   `yaml:"drift_threshold"`           // 默认 3
	LocalizationRunThreshold int   `yaml:"localization_run_threshold"` // 默认 3
}
```

**为什么用 `*bool` 而不是 `bool`。** Go 的 bool 零值是 `false`，无法区分
"用户显式写了 false"和"用户没写、走默认"。而这两个默认值恰好一真一假
（反思默认开、周期兜底默认关），没有指针就无法同时表达"有默认"和"可覆盖"。

`IsEnabled()` / `IsPeriodic()` 把 nil 翻译成默认值，调用方不必关心指针。

**mergeConfig 逐字段覆盖，不能整体赋值。** 如果写成
`if override.Reflection != (ReflectionConfig{}) { base.Reflection = override.Reflection }`，
本地层只写一个 `max_wait_ms` 就会把上层显式设置的 `enabled: false` 冲掉。
指针字段为 nil 表示"未设置"，逐字段判空即可。

### 2.4 `internal/tui/tui.go` / `internal/remote/server.go` / `cmd/tencoder/main.go`（改，装配）

两侧**对称**接法——headless 会话里悄悄没有偏移检测，是一种 bug 而不是简化。

```go
reflector.OnDrift = func(taskName, output string) {
    m.taskWriter.OnSubTaskComplete(context.Background(), taskName, output)
}
```

**任务 2.4 的接线只有一行**，因为 `ReflectionDriftSink` 的签名
`(taskName, output string)` 和阶段一 `TaskWriter.OnSubTaskComplete` **逐字相同**。

## 3. 设计哲学（面试可讲）

1. **裁判必须在主上下文之外。** 复用主 client 就没有"第三方"可言；
   独立 system prompt + 独立 client 是这个机制成立的前提，不是实现细节。

2. **"最新"按序号，不按到达顺序。** 并发完成顺序不可控；
   按到达顺序顶掉会把过时判定喂给主循环。**这一条值得单独准备，它是并发正确性的硬考点。**

3. **判定无效是第三态，且不计窗口。** 裁判坏了不能变成"持续告警"，
   更不能变成"静默通过"。K 窗口计的是 agent 偏了几次，不是裁判吐了几次字。

4. **注入的是"某个观察者的看法"，不是系统断言。** reminder 里显式写了
   "treat that observation as one reviewer's reading, not as a verdict"。
   这让一次误判的 No 不会因为措辞权威而被盲从——防抖不能只靠计数器，也要靠措辞。

5. **系统自己注入的 user 消息不是任务目标。** plan reminder、工具清单、auto memory 头
   都是 user 角色。当成目标会凭空制造误报。

6. **全链路静默。** 裁判超时、报错、返回垃圾、对话为空——每条路径都不阻塞主循环。
   漏拦一次的成本远小于卡死一次对话。

7. **偏移只在硬处置时沉淀成记忆。** 软提醒不写 task 记忆。
   否则 agent 每被提醒一次就产生一条"我又偏了"，`tasks/` 会被自造的噪声灌满。

## 4. 踩坑记录

### 4.1 `-race` 抓出两个问题（一个是测试脚手架，一个是真 bug）

**测试脚手架的竞态**：`scriptedJudge` 原来返回 `(*int32, *sync.Mutex)`，
测试代码用一把**新 mutex** 去读计数，而裁判 goroutine 用的是**另一把锁**写入。
典型的"锁配错了对象"。改成返回 getter 闭包，让读写共用同一把锁。

**生产代码的真 bug**（顺着 race 报告查出来的）：`Fire` 的空输入守卫判错了对象，
详见 §2.1.3。**race detector 报的地址在测试文件里，根因却在生产代码里**——
这类间接线索值得追下去，否则就只是"修了个测试"。

### 4.2 一个 flaky 测试暴露了 goroutine 调度的不确定性

`TestLatestVerdictOverwritesOlder` 第一版用"调用序号"区分新旧两次 judge 调用，
结果时好时坏。原因是 `Fire` 启动的两个 goroutine **谁先跑不确定**，
所以"call 1"未必对应"fire 1"。

改成按**快照内容**区分（`strings.Contains(userMsg, "state two")`）——
快照是确定的，调用次序不是。**测试里凡是用"第几次调用"当标识符，
都要先确认 goroutine 启动顺序是有保证的；这里没有。**

### 4.3 修复了阻塞 `internal/agent` 整包测试的既有 mock

`agent_test.go` 里 `mockClient` / `dynamicMock` 都没实现 `llm.Client` 的
`SetSystemPrompt`，导致整个包的测试二进制编译不过——**新增的 27 个用例一个都跑不了**。

补了两个空实现方法。这是既有遗留问题（与阶段二无关），但不改就跑不了自己的测试。
`internal/memory/extractor` 里有同样的问题，未一并处理（那里只有既有用例，
不阻塞验证）。

### 4.4 `internal/config` 的包测试同样被既有问题阻塞

`media_providers_test.go` 引用了未定义的 `MediaProviderConfig`（`internal/media` 包缺失），
导致 config 整包测试编译失败。

`MediaProviderConfig` 属于另一个未实现的功能，**顺手补它等于凭空发明一个功能**，
不在本阶段范围内。改用一个放在模块内的临时程序验证配置语义（验证完即删），
覆盖了指针默认值、逐字段覆盖、零值默认三组断言，结果全绿。

**这是一个明确的验证缺口**，如实记在这里：`mergeConfig` 的 reflection 分支
没有跑在 `go test` 里，靠临时程序验证。

### 4.5 `Config.Logf` 写错位置

第一版把 `Logf` 塞进了 `agent.ReflectionConfig`，编译报错——它属于 Reflector 不属于配置。
配置项是**要被用户写的 YAML**，往里塞回调函数会让配置结构不可序列化。
