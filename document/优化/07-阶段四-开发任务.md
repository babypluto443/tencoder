## 0. 设计总纲（一句话版）

- **跨项目安全靠沙箱 + 审批链，不靠 worktree**——worktree 是冲突边界不是安全边界（共享 .git 有 hook 注入面），面试主动讲这个 trade-off。
- **审计是旁路（零阻塞），审批是升级（只读项目专属）**——不新增确认环节，不让"确认"变成骚扰。
- 进度接口是**查询模型**：何时关心进度的决定权在 lead 自己手里，进度噪声不进上下文。

## 1. 现状事实（代码摸底结论）

- `internal/teams/progress.go` 已有 `TeammateProgress`（工具活动/token/状态，喂 TUI）；`internal/agents/agent_tool.go` 已有 `SubAgentProgress` 结构化事件通道；team 模式 lead 通过 mailbox + SendMessage 协调——缺的是 **lead 主动拉取结构化汇总的入口**。
- `internal/permissions` 五层已分好：危险命令 / `PathSandbox`（allowedRoots+denyWrite）/ 规则引擎 / 会话放行 / 审批模式；**`PathSandbox.Check` 不区分读写**——"允许读、拒绝写"是结构缺口。
- 写前确认已存在（`PermAllow/PermDeny` 审批流）——4.2 真正增量是**审计日志（完全没有）**和只读项目写处置。
- `internal/worktree` 已相当完整（per-agent worktree、session worktree、变更追踪、清理）——4.5 增量是**跨项目注册与绑定**。

## 2. 分支决策记录（grill-me 定案）

### A. workspace 注册表（4.3/4.4）

| 决策点 | 定案 |
|---|---|
| 注册方式 | `.tencoder/workspaces.yaml` 声明式（项目路径 + 级别），会话启动加载；`/workspace` 会话内命令运行时注册（演示现场加项目不用改配置重启） |
| 级别模型 | 两级：`writable`（直接可写）/ `readonly`（读自由，写触发显式审批链）。不做第三级 |
| 沙箱接入 | `PathSandbox` 新增 `readonlyRoots`；`Check` 拆为 `CheckRead`（allowedRoots ∪ readonlyRoots）与 `CheckWrite`（仅 allowedRoots）；只读写尝试返回带项目名的拒绝信息 |
| 子 agent 绑定 | spawn 时可选指定 workspace——子 agent sandbox 只含 `主项目 + 该 workspace`，其余注册项目对其不可见（隔离到"子 agent 视野"） |

### B. 审计日志与只读写处置（4.2）

| 决策点 | 定案 |
|---|---|
| 审计挂点 | `Checker.Check` 返回写类决策时（Allow/Ask/Deny 都记），**异步**追加 JSONL 到 `.tencoder/audit/audit-YYYYMMDD.jsonl`；fire-and-forget，审计绝不阻塞主循环 |
| 审计字段 | 时间、会话 ID、agent 名（谁）、工具、目标文件（哪个文件）、动作摘要（做了什么写）、决策结果 |
| 只读项目写 | 不是 Deny 了事——升级为**显式审批链**：强制 Ask 且**禁用 AllowAlways**（防手滑永久放行破坏只读语义）；批准 → 放行并记 `approved-by-user`；拒绝 → 记 `denied-readonly` |
| 可写项目 | 现有审批流原样工作，审计只记录不拦截——**不做双重确认** |
| "写前确认钩子"的准确含义 | 不是新加确认，而是把只读项目写从静默拒绝升级为带审计的显式审批 |

### C. 跨 Agent 进度接口（4.1）

| 决策点 | 定案 |
|---|---|
| 形态 | 新增 **`GetTeamProgress` 查询工具**：lead 主动调用，返回全部在跑子 agent 的结构化汇总（名称/状态/最近动作/工具调用数/耗时/token） |
| 数据源 | 复用现有 `TeammateProgress` + `TaskManager`，**零新状态** |
| 完成事件 | 走现有 mailbox 通知（已存在），lead 平时安静、想知道细节就查 |
| 否掉的方案 | 事件注入（每次工具调用都进 lead 上下文 = 进度噪声淹没对话，与"而非全文粘贴"初衷相悖） |

### D. worktree 策略（4.5，直接拍板）

- **主路径：审批链直写**——跨项目写经显式审批后直接写目标项目（已有人工把关；绕 worktree 避免额外合并负担）；
- **并行场景用 worktree**：team 模式下多个子 agent 分配到**同一个可写 workspace** 并行干活时，用现有 `CreateAgentWorktree` 在该项目内建 per-agent worktree（单项目能力平移到注册 workspace，代码基本复用）；
- **新增管理命令**：`/workspace` 命令带 worktree 子命令（list/create/cleanup），复用现有 cleanup/changes 模块。

### E. 验收口径（直接拍板）

- **验收 1（60% 优势）**：同一跨文件重构任务（3+ 文件、文件间有依赖），单 agent vs 3 子 agent 并行两组各跑 ≥5 次取耗时均值，实测对比——沿用阶段二/三"实测不引用"的口径哲学；
- **验收 2（互不污染演示）**：用两个真实项目（tencoder + pluto_feed），一个会话内注册并修改两个项目，验证改动分别落在各自项目、审计日志分列记录；
- **验收 3（只读拒绝）**：把 pluto_feed 注册为 readonly，尝试写 → 强制审批 → 拒绝 → 审计日志 `denied-readonly` 完整记录；
- **验收 4（全量可追溯）**：所有写操作（含批准放行的只读写）在审计 JSONL 中逐条可查。

## 4. 验收标准（自任务书，口径已定）

1. 跨文件重构任务耗时保持单 Agent 对比约 60% 的优势不回退（实测口径见 E）；
2. 演示"一个对话窗口内同时修改两个项目且互不污染"（tencoder + pluto_feed 实景）；
3. 只读项目的任何写尝试被拒绝，且审计日志有完整记录（`denied-readonly`）；
4. 所有写操作在审计日志中可追溯（文件级，含批准放行的只读写）。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| worktree 共享 .git 的 hook 注入面 | 明确定位：worktree 只做冲突隔离，安全靠沙箱+审批链；注册 workspace 时校验其 .git/hooks 归属 |
| 双重确认骚扰 | 可写项目零新增确认；只读项目审批禁用 AllowAlways，一次一确认 |
| 审计日志膨胀 | 按日分文件；只记写类决策；JSONL 追加写无锁竞争（单 writer goroutine） |
| 只读级别被绕过（Bash 间接写） | `CheckWrite` 对 Bash 类命令做路径提取（复用现有 extractFilePath 思路）进只读校验；开发记录写明覆盖边界（重定向等复杂命令仍靠 Layer 1 危险命令检测兜底） |
| 60% 数字受任务结构影响 | 固定同一任务、同模型配置，只变"单 agent vs 并行"一个变量；各 ≥5 次取均值 |
