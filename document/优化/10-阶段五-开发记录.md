## 0. 一句话

给整条链路装上**两档模型**：声明式分类定基线、两个运行时信号只能升不能降；轻量档写出来的代码过一道秒级语法门禁，不过就续作修复（只修一次）。目标 token −45%、延迟 −31%、轻量档占比 ≥60%。

## 1. 逐文件详解

### 1.1 `internal/llm/router.go`（新增，443 行）

路由核心。三层结构刻意分开：

| 层 | 职责 | 为什么不合并 |
|---|---|---|
| `TaskClass` 八类枚举 + `BaselineTier` | 声明信号 → 基线档位 | 纯数据，可穷举 |
| `Decide(class, hints, cfg)` | 纯函数裁决，返回 `(tier, reason, promoted, suppressed)` | **不构造 client**，所以能穷举测试；`Resolve` 只负责把 tier 变成一个能用的 client |
| `Router.Resolve(class, hints)` | 实际选模型、造 client、填 `RouteResult` | 唯一碰 `NewClient` 的地方 |

**八类与基线：**

| class | 基线 | 为什么 |
|---|---|---|
| `memory_recall` | light | 读标题+描述做选择，最高频的旁路调用 |
| `log_summary` | light | 压缩超长输出是摘要 |
| `format_check` | light | 检查类判定 |
| `explore` | light | 检索与试读；但它会改文件，所以门禁要盯（见 4.4） |
| `patch_gen` | strong | 生成代码 |
| `arch_decision` | strong | 架构决策 |
| `conflict_merge` | strong | 冲突合并 |
| `cross_project` | strong | 跨项目改动 |

**两个运行时信号（只能升档）：**

```go
overBudget := hints.EstimatedToolCalls > 0 && hints.EstimatedToolCalls > cfg.ToolCallBudget
bigContext := hints.ContextTokens    > 0 && hints.ContextTokens    > cfg.ContextTokensThreshold
```

`> 0` 那两处是刻意的：**0 表示"未知"，不是"极小"**。少了这个判断，一个"我们不知道要多少次工具调用"的任务会被当成 0 次而路由到便宜模型——这是阈值系统里最危险的形态。单测 `TestZeroHintsAreUnknownNotZero` 专门盯它。

**没有降档信号。** 三条理由：省的钱远小于"轻量模型写了个错补丁、主 agent 的测试循环又调回来重做"的成本；阶段四已有一套"可写/只读"的分级，没理由在模型侧再来一套语义；且降档需要一个"这个任务很简单"的判据，而那正是 taskClass 已经在做的事，再叠一层信号只会产生两个互相矛盾的真相。

**`ExplicitModel` 短路在 router 层而不是 `Resolve` 之后**——这样日志里绝不会出现"路由调整了默认值"这种对一个被用户显式指定了模型的运行的描述。

**`Resolve` 的三处回退全部朝"更贵、同样结果"方向：**

- 无 light 模型配置 → 留在会话模型（标注 `Reason`）
- 显式模型不可用 → 落回该档默认（`Reason` 里带原因）
- `NewClient` 失败 → 落回 session client

**路由失败绝不能变成"任务不跑了"。**

### 1.2 `internal/llm/qualitygate.go`（新增，318 行）

门禁三件套：`go build` / `go vet` / `gofmt -l`。

- **不进完整测试**：任务书决策 B。主 agent 发现测试失败自然反馈，那是 agent 行为；门禁塞分钟级测试会把 −31% 延迟吃掉。
- **缓存**：`goModuleRootFingerprint(dir)` = 文件数 + 最新 mtime，落盘在 `~/.tencoder/gate-cache/`。一键 Ctrl+C 重进的项目能省掉冷 module cache 的那次 build。
- **`Skipped` 是中性态**：非 Go 目录返回 `{Skipped:true, Passed:true}`。判成失败会导致非 Go 项目每次都触发一次无意义的升级；判成"通过"又会掩盖问题——所以单测 `TestGateSkipsNonGoDir` 明确断言 `Skipped && Passed` 同时成立。
- **`TimedOut` 与 `Passed=false` 分开**：超时不等于代码有问题，调用方据此不升级（见 4.3）。

### 1.3 `internal/agents/agent_tool.go`（改）

新增字段 `Router` / `QualityGate` / `GateEnabled` / `LogRoute`；`SubAgentSpec` 加 `Tier` / `TaskClass`；新增 5 个函数。

**`selectClientForSpec` 与旧 `selectClient` 并存**——`Router == nil` 时走旧路径。这不是冗余，是**让"未装配"与"装配但未路由"这两件事在代码上可区分**；也让所有既有测试不需要改一行就继续通过。

**`spec.Tier = tier` 写在 spec 上而不是局部变量**：`shouldGate` 与升级提示词都要读它，局部变量它们看不见。这是阶段一到四反复出现的同一个模式（阶段一的 `writeSeenAfterRun`、阶段二的 `fireSeq`）——**决定必须落在会被后续读到的那个对象上**。

**`spawnRepair` 不走 `runSync`**：走 runSync 会重新推导 client、重新建 worktree、**重新进门禁**——于是一次失败的修复会递归触发另一次升级。防循环的边界不能只靠"最多 1 次"这个计数器，必须靠**修复路径与主路径在结构上不相交**。

修复 agent 强制补 Bash 工具：不能跑编译器的修复 agent 无法验证自己的修复，而"未经验证的修复"正是这个阶段想避免花两次钱买的东西。

### 1.4 `internal/agents/definition.go`（改）

`AgentDefinition` 加 `taskClass: string`，`ToSpec()` 走 `llm.ParseTaskClass`。

**不校验成 error。** 一个拼错的路由提示不该让一个能用的子 agent 下线；且拼错的方向是"未分类"，而未分类落强档——安全方向自动成立。

### 1.5 `internal/config/config.go`（改）

`RoutingConfig`：`disabled` / `tool_call_budget` / `context_tokens_threshold` / `light_model` / `strong_model` / `gate_enabled` / `gate_timeout_ms`。

两个布尔用 `*bool`，理由同阶段二/三的 `ReflectionConfig`：**默认值不同向时（一个默认 true 一个默认 false），非指针无法区分"没写"和"写了 false"。**

`mergeConfig` 逐字段覆盖，14 处 `override.Routing.*`。**逐字段而非整体赋值**，否则项目层只想关掉门禁，就得把用户层的 `light_model` 一起冲掉。

### 1.6 `internal/tui/tui.go` / `internal/remote/server.go`（改）

新增 `routedSideCall`（两侧对称），把五个旁路装配点收口成一次调用。

**收口前的现状**：memory 提取 / memory 蒸馏 / memory selector / 反思裁判 / 工具结果摘要，各自持有一段近乎逐行相同的 `NewClient + Stream + token 归集`。五份实现意味着改一次 token 口径要改五处，**漏一处就有一处埋点失真，而失真是静默的**。

收口后：

```go
out, in, out2, err := m.routedSideCall(ctx, llm.ClassMemoryRecall, sysPrompt, userMsg, timeout)
```

`routeDebugf` 走 stderr 而非聊天渲染——埋点是 5.5 的口径数据，不是界面元素，混进 Bubble Tea 视图会破坏布局。

`installRouting` 必须在 `registerAgentTools` **之前**调用：AgentTool 只持有指针，顺序反了会拿到永远 nil 的 router，于是**所有任务静默走强档**——而这看起来像"路由开了但没效果"，是最难查的一类症状。

## 2. 设计哲学

### 2.1 声明是第一信号，信号只能往上推

分类写在 agent 定义里，是人（或写定义的人）能审阅、能 review diff 的东西。运行时信号是机器的补充判断。让机器能覆盖人的声明，等于让一次无人审阅的成本变更悄悄生效。

对应代码：`promoted && base == TierLight` —— 只有 light 基线能被推上去，强档无从再升。

### 2.2 0 是"未知"

阈值系统最常见的缺陷形态：把"没有数据"编码成"数值为零"，再拿零去和阈值比。后果是**信号越缺失、路由越激进**——正好和直觉相反。`> 0 &&` 两处是这条原则的代码形态。

### 2.3 所有回退都朝"更贵、同样结果"

无 light 模型 → 留强档；client 构造失败 → 落回会话模型；路由未装配 → 旧行为。**统一的不变量是：路由层出任何问题，用户只会多花钱，不会少拿结果。**

### 2.4 门禁是"语法层安全网"，不是质量裁判

编译不过、vet 报错、gofmt 不合规——机械可判。逻辑对不对门禁不关心，那是主 agent 测试循环的职责。这条分层要主动讲（任务书风险表已列）：**声称门禁保证质量是不诚实的；声称它是廉价的前置拦截是准确的。**

### 2.5 防循环靠结构，不靠计数器

`spawnRepair` 走独立路径，不重入 runSync。计数器 `最多 1 次` 是第二道保险；第一道是"修复路径压根不经过升级入口"这个结构事实。**只靠计数器的防循环，在有人给修复路径加一行 `runSync` 的那天就失效了。**

### 2.6 超时不升级

超时意味着工具链慢（module cache 冷、vet 挂住），不是轻量模型写坏了代码。在这里升级是**花一次强档调用修一个不存在的问题**。

## 3. 与任务书的偏差

| 任务书 | 实现 | 理由 |
|---|---|---|
| `Resolve` 返回 `(client, tier, reason)` 三元组 | 返回 `RouteResult` 结构体 | Go 表达不了 3 元组 + 额外字段，而评测报告需要 `model` / `promoted` / `suppressed` |
| 门禁触发范围"声明为代码生成类且走 light 档" | 同 | 但实现上**只用 class 谓词判"是否写代码"**，见 4.4 |
| 升级标记进埋点 | `LogRoute` 输出 `[gate] escalated → strong` 一行 | 不新增持久化结构；埋点口径与阶段一/二/三一致（单行 stderr + `TENCODER_LLM_DEBUG`） |

## 4. 踩坑

### 4.1 `gateDir` 一度设在 worktree 创建之前

最初写在 `runSync` 开头，接着发现紧跟其后的就是 `subAgent.WorkDir` 的赋值——**门禁会去检查 agent 根本没改过的那棵树**，于是一份编译不过的 worktree 代码能通过门禁。

**顺序本身就是语义**：隔离分支必须先跑完，门禁才知道该看哪儿。

### 4.2 门禁一度排在 worktree 清理之后

改对 `gateDir` 之后仍然错：如果先清理 worktree 再跑门禁，修复 agent 拿到的是一个已删除的目录。

这个 bug 的形态值得记：**两处各自都"看起来对"，只有它们的相对顺序才决定对错。** 单测全绿时它不会暴露——因为单测里没有 worktree。

现在门禁在清理之前：如果门禁触发了修复，worktree 因有改动而被保留，修复在正确的目录里进行。

### 4.3 升级 client 一度用 `ExplicitModel: "strong"` 这个假模型名

`sentinel handled below` —— 下面并没有 sentinel。`modelAliases["strong"]` 不存在，会走"当字面模型名用"分支，去向一个叫 `strong` 的模型。

改成按 `ClassPatchGen` 解析（其基线本就是 strong）。附带一条设计要点：**升级不重跑当初把我们降到 light 的那些信号**——工具预算超了就是超了，重问一遍只会再被降回去。

### 4.4 `shouldGate` 里多写了一个基线条件（测试抓出来的）

我最初写成：

```go
return llm.BaselineTier(spec.TaskClass) == llm.TierLight && isCodeGenClass(spec.TaskClass)
```

推理是"写代码的类应该基线是 strong"。这个推理**把"这个类通常多贵"和"它的输出要不要编译"混成了一件事**，而且 `patch_gen` 的基线正是 strong——所以 spec 说 light 时这个条件恒假，**门禁对它要保护的那个类永远不触发**。

单测 `TestShouldGateOnlyForLightTierCode` 第一条就红了。

现在条件只有 `isCodeGenClass`。**诚实的后果一并写进注释**：路由当前只升不降，`patch_gen` 到不了 light 档，所以今天实际会触发门禁的是"light 档 explore 且改了文件"这类运行；`patch_gen` 那一支是防御性的，等出现降档信号或按类指定模型的 pin 时才真正生效。

### 4.5 `internal/remote/server.go` 里两个 helper 丢失

批量文本编辑时把 `mustGetwd` 和 `newAgentHookRunner` 连带删掉了（编译报错才暴露）。仓库**不是 git 仓库**，无法 checkout 恢复。

按 TUI 侧的同名实现重写补回，两处都对照了调用点的实际用法（`mustGetwd` 用于 websocket 握手上报 cwd，`newAgentHookRunner` 是 `type: agent` hook 的 runner）。

**这件事记在这里是因为它有后果**：这个仓库没有版本控制，本阶段所有改动都无法回滚。后续动手前值得先 `git init`。

### 4.6 配置合并块第一次插入静默失败

`str.replace(anchor, ...)` 的 anchor 因为 gofmt 对齐差异没匹配上，脚本没报错、合并逻辑没插进去，**而 `go build` 依然通过**（少一段逻辑不影响编译）。

发现方式是我自己写的校验程序：本地层写 `tool_call_budget: 10` 期望覆盖 30，读回来还是 30。

**"配置不生效"这种 bug 编译期和绝大多数单测都抓不到**——它只在一个用真实三层路径加载配置的检查里可见。这也是为什么这一项值得单独跑一个校验程序。

### 4.7 校验程序自己错了两次

- 第一版用 `LoadConfig(path)` 加载两个文件对比——但 `LoadConfig(path)` 只加载单文件，合并只发生在无 path 分支。测的是不存在的行为。
- 第二版改走 `LoadConfig("")` 真实合并后，又把**合并后**的值当作用户层的值断言（"用户层应保留 30" vs 实际已被本地层改成 10）。

最终拆成 [A] 单层解析 与 [B] 三层合并 两组共 13 条断言。**逐层解析与跨层合并是两件事，混在一起断言就会得到看似矛盾的结果。**

## 8. 已知边界

1. **`patch_gen` 实际到不了 light 档**（见 4.4）。轻量档占比的目标要靠 `explore` / `memory_recall` / `log_summary` / `format_check` 达成，而不是 `patch_gen`。
2. **`EstimatedToolCalls` 目前没有生产调用方**。`RouteHints` 字段在，`Decide` 会读，但 `selectClientForSpec` 目前只填 `ExplicitModel`。**工具预算是这一阶段最有价值的信号，也是唯一还没接上的一个。**
3. **门禁只认 Go**。Python / TS 项目直接 skip。任务书如此，但面试时要主动讲这个边界。
4. **`spawnRepair` 里权限请求一律 auto-allow**。修复 agent 卡在审批弹窗上就完不成修复；沙箱边界仍在，去掉的是摩擦不是约束。
