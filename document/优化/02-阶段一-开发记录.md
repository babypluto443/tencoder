## 0. 这一阶段到底加了什么

一句话：**给现有的两类型记忆体系（user/feedback/project/reference）补上第三层——短期任务记忆**。

改动前，一个子任务踩过的坑只在当次对话里有意义，对话一关就没了。下次同类任务会重新踩一遍。
改动后，子 agent 收尾时把「踩了什么坑 + 为什么会这样 + 怎么绕过去」结构化落盘成一条 task 记忆；
下次新开会话，召回器会把这条例教训选出来喂给 agent。

三层各自的职责，用一句话锚住（这也是面试叙事的锚点）：

| 层 | 存什么 | 生命周期 | 存在哪 |
|---|---|---|---|
| 工作记忆 | 当前对话 | 会话内，两层压缩续命 | 会话内存 |
| **短期任务记忆** | **过程中得到的教训** | **子任务完成 → 蒸馏 → 删除（暂存态）** | **`.tencoder/memory/tasks/`** |
| 长期项目记忆 | 世界的状态 | 长期，靠 update/merge/skip 控膨胀 | `.tencoder/memory/` 根目录 |

## 1. 逐文件详解

### 1.1 `internal/memory/memory_types.go`（改）

**改了什么**

1. 新增第五个类型 `TypeTask`。
2. `ParseMemoryType` 从遍历 `MemoryTypes` 改为遍历新增的 `parseableTypes`。

**这里有个容易踩的坑，值得单独讲**

`MemoryTypes` 这个导出变量不只是「能解析哪些类型」，它同时是**暴露给模型看的可写分类法**——
`TypesSectionDualPath` / `TypesSectionIndividual` 两段提示词里列的就是这四个。

如果图省事把 `task` 直接加进 `MemoryTypes`，模型就会开始自己写 task 记忆。而 task 记忆是
**系统写的暂存态**：它的整个生命周期（写入、蒸馏、删除）由代码控制，模型插一脚就坏了。

所以拆成两个变量：

```go
// 模型可写：四类
var MemoryTypes = []MemoryType{TypeUser, TypeFeedback, TypeProject, TypeReference}

// frontmatter 能解析的：四类 + task
var parseableTypes = []MemoryType{TypeUser, TypeFeedback, TypeProject, TypeReference, TypeTask}
```

解析器认 `task`，模型提示词里没有它。这是「解析」和「授权」的分离。

**3. WhatNotToSave 拆成两条（对应决策 B）**

原来那节叫 `WhatNotToSaveSection`，是一份**黑名单**（别存代码模式、别存 git 历史……）。
黑名单对模型写记忆有效，但对 task 记忆不够用——黑名单挡不住"动作流水账"这种新形态的垃圾。

所以拆成：

- `WhatNotToSaveSection`（旧规则原样保留，开头加一句「以下规则适用于你自己写的四类」）；
- `WhatNotToSaveTaskSection`（**白名单**，只允许四样：踩坑及原因 / 恢复路径 / 用户口头约束 /
  对后续工作的影响），后面紧跟一份明确的「禁止项」清单。

关键设计：`WhatNotToSaveTaskSection` 不只给模型看，它被 `TaskExtractionSystemPrompt`
**原样内嵌**进提取提示词。也就是说这份白名单在代码里只有一份定义，
设计文档写的规则和模型实际看到的规则不可能跑偏。

### 1.2 `internal/memory/paths.go`（改）

新增三个东西：

```go
const TaskMemDirName = "tasks"

func GetTaskMemPath(projectRoot string) string        // <root>/.tencoder/memory/tasks/
func EnsureTaskMemDirExists(projectRoot string) error // 幂等建目录
func IsTaskMemPath(absolutePath, projectRoot string) bool
```

**一个值得注意的点：`IsAutoMemPath` 一行没改，tasks/ 就已经被沙箱放行了。**

因为 `IsAutoMemPath` 是对 memory 根目录做**前缀匹配**：

```go
strings.HasPrefix(abs+string(filepath.Separator), dir)
```

`dir` 是 `.tencoder/memory/`，那么 `.tencoder/memory/tasks/x.md` 天然命中。任务书里
「`IsAutoMemPath` 认账 tasks 子目录」这一条，实现方式是**确认既有逻辑已经覆盖，然后写进注释说明为什么**，
而不是加一段新判断。这是「读代码再改」的价值——如果照字面新加一个 tasks 判断分支，
反而是在既有前缀语义上叠一层冗余。

**为什么 task 记忆只在项目级，没有用户级？**
一个仓库里踩的坑拿到另一个仓库没有意义。所以 task 记忆没有 user-level 目录。
（`TENCODER_REMOTE_MEMORY_DIR` 那个 escape hatch 仍然生效，因为它覆盖的是整棵记忆树。）

### 1.4 `internal/memory/find_relevant_memories.go`（改，含一个真 bug 修复）

**改了什么**

1. `SelectMemoriesSystemPrompt` 补了一段 task 类型的说明（决策 F 的「软引导 1」）：
   告诉选择器 task 记忆是「近期任务踩过的坑与恢复路径」，续做/修复类查询优先考虑，
   同时明确它们**和其他记忆一样争那 5 个槽位、没有硬配额**。
2. `validFilenames` 和 `byKey` 扩容。

**这里发现并修掉了一个既有 bug**

原代码：

```go
// 清单里渲染的是 m.FilePath（绝对路径）
fmt.Fprintf(&b, "- %s%s%s (%s): %s", scope, tag, path, ts, m.Description)

// 但白名单只收了 m.Filename（相对文件名）
validFilenames[m.Filename] = struct{}{}
```

清单给模型看的是绝对路径，白名单却只认相对文件名。模型照着清单回显绝对路径 → 被过滤掉 →
**一次正确的选择被静默丢弃**。

在只有顶层文件时，`Filename` 恰好等于 basename，模型也可能回显 `foo.md`，所以这个 bug
一直潜伏着。引入 `tasks/foo.md` 之后两种形态的差异变大，问题就从「偶发」变成「必然」。

修法是**三种形态都认**：绝对路径、目录相对路径、裸文件名。

```go
validFilenames[m.Filename] = struct{}{}
validFilenames[m.FilePath] = struct{}{}
validFilenames[filepath.Base(m.Filename)] = struct{}{}
```

`byKey` 同理，并且裸文件名冲突时 first-wins——宁可召回错一条，也别把正确的那条丢掉。

**注意这个 bug 不在任务书里**。它是「加子目录扫描」这个需求撞上「清单与白名单形态不一致」
这个既有隐患的产物。开发记录留这一节，是想说明：验收清单只能证明你做了要求的事，
证明不了你没碰坏别的事。

### 1.5 `internal/memory/task_write.go`（新增，296 行）

子任务完成 → 结构化落盘一条 task 记忆。

**接口注入的形状**

```go
type TaskExtractorFn func(ctx context.Context, systemPrompt, userMessage string) (string, TaskExtractionUsage, error)

type TaskExtractorUsage struct {
	InputTokens  int
	OutputTokens int
}
```

抄的是 `find_relevant_memories.go` 里 `SelectorFn` 的模式：**memory 包不在包级依赖 llm**。

为什么不直接传 `llm.Client`？三个原因：

1. `memory` 被 `memory/extractor` 依赖，而 extractor 又依赖 `agents`、`agent`、`llm`——
   直接依赖容易绕成环。
2. `llm.Client` 是「流式 + 已绑定 system prompt」的接口，调用方每次都要现造一个 client；
   而这里的 LLM 调用是**一次性旁路查询**，语义上就是「给我 system prompt，返我一段文本」。
3. 测试可以直接注入假函数，不需要 mock 整个流式协议。

`TaskExtractionUsage` 是自己定义的普通结构体而不是 `llm.UsageInfo`，同理：解耦。
**但它是有代价的**——usage 的填充责任转移到了调用方（TUI 侧），如果那边忘了填，
验收标准 3 的 token 数据就是 0。这一点在 1.7 里再提。

**失败即静默**

`OnSubTaskComplete` 的每一条错误路径都是静默 return。理由写在代码注释里：

> 缺一条 task 记忆，代价是未来某次会话重新踩一次坑；
> 而记忆子系统一旦 panic 或阻塞，代价是用户丢掉了当前这次对话。

这个取舍和现有的「召回失败即不召回」是同一条哲学：**记忆是增强，不是依赖**。

**四段结构是检查清单，不是模板段落**

决策 C 明确说 `目标 → 动作序列 → 踩坑+恢复 → 结果` 是**生成端检查清单**。
落地方式：

- **目标**：压成一句话进 frontmatter `description`，**正文不重复**；
- **动作序列**：只保留转折点，字段叫 `pivots`，可省略，最多 3 条；
- **踩坑 + 恢复路径**：正文主体，**必填**，缺一整条记录作废；
- **结果**：一句话 + 对后续工作的影响。

正文渲染（`TaskRecord.Body()`）刻意不写「目标」段落——目标已经在 description 里了，
再写一遍就是浪费召回时的 token。

**拒绝半成品记录**

```go
if desc == "" || pitfall == "" || recovery == "" || name == "" {
    return TaskRecord{}, false
}
```

宁可一条不写，也不写一条「有坑没恢复路径」的记录。理由写在注释里：
**一条没有行动指引的教训，被召回出来时读者无法据此行动，比不召回更糟**——它会占用 5 个槽位之一，
挤掉真正有用的记忆，同时给出一个无法执行的警告。

**文件名用内容派生而不是 task ID**

```go
// hardcoded-fixture-path.md  而不是  task_3_20261016.md
```

理由：手工翻 `.tencoder/memory/tasks/` 排查时，文件名本身就是信息。冲突时加数字后缀。
`name` 字段还要过一遍 `slugCleaner`（只留小写字母数字，其余转连字符），防止模型吐出带 `/`
的路径型 name——那会直接造成目录穿越。

**description 的换行必须压掉**

```go
descCleaner = regexp.MustCompile(`[\r\n\t]+`)
```

frontmatter 是行解析的。description 里有一个换行，字段就在那里被截断，
产出一份扫描器读不出来的 header，而且**不报错**——静默损坏比报错更难查。

**输出只取尾部 24KB**

子 agent 的 output 是 200 轮流式文本拼出来的，没有上界。坑（如果有）几乎总在收尾那段
（agent 汇报发现了什么）。取尾部 `MaxTaskExtractionOutputBytes = 24KB`，
让这次调用的输入 token 可预测。

### 1.6 `internal/memory/task_consolidate.go`（新增，557 行）

空闲蒸馏：task 记忆 → 长期记忆 → 删源。

**并发保护（任务书要求单列一节）**

```go
if !c.inFlightMu.TryLock() {
    c.logf("[task-consolidate] skipped — a round is already in flight")
    return 0
}
defer c.inFlightMu.Unlock()
```

用 `sync.Mutex.TryLock` 而不是 `bool` 标志位。差别在于：`bool` 的
「检查 → 置位」不是原子的，两个触发源（空闲定时器 + 堆积兜底）撞上时会同时跑两轮；
`TryLock` 把判断和占位合成一步。

`TryLock` 放在函数**第一条语句**——先占位再做任何 IO，
这样第二个调用者一定在第一个还没读完文件时就返回了。

**空闲判定用「重臂定时器」而不是 sleep-then-check**

```go
func (c *Consolidator) NotifyActivity() {
    c.lastActivity = time.Now()
    c.timer.Stop()
    c.timer = time.AfterFunc(c.deps.IdleWindow, func() { c.runIfIdle() })
}
```

`sleep(60s); if idle { run() }` 和这个的区别是：前者在 sleep 期间用户打字，
醒来时得重新判断——而一旦判断为"不空闲"，这轮就白等了，得再等一个完整周期。
后者每次新输入都把截止点**往后推**，用户连续打字就永远不会被打断。

定时器回调里还要再查一次 `lastActivity`：

```go
func (c *Consolidator) runIfIdle() {
    idle := time.Since(c.lastActivity) >= c.deps.IdleWindow
    if !idle {
        c.NotifyActivity()  // 重新计时，而不是放弃这一轮
        return
    }
    c.Run(context.Background())
}
```

`NotifyActivity` 和定时器武装之间存在竞态窗口，回调里这一查堵的就是它。

**四个动作，以及为什么是四个**

```go
ActionCreate / ActionUpdate / ActionMerge / ActionSkip
```

动作种类是刻意的约束，不是分类学。「部分有用」这个选项必须不存在——
一旦存在，模型就会选它，然后你要处理一种既没落进长期记忆、
源文件又该不该删的中间态。现在必须二选一。

**update 用追加，merge 用覆盖**

这是整个文件里最需要解释的一处不对称。

蒸馏器**看不到**现有长期记忆的正文——它只拿到清单（filename + description）。
正文会给 token 预算带来平方级的浪费（清单 × 正文 × 文件数），
而蒸馏器的任务是**路由**（这份教训该去哪），不是重写。

于是：

- **update**：模型只被允许输出「要新增/要纠正的部分」。因此代码侧**只能追加**，
  不能覆盖——覆盖就会销毁模型根本没看到的内容。追加时打一行 HTML 注释标记来源：
  ```go
  b.WriteString("\n<!-- consolidated from a task memory -->\n")
  ```
- **merge**：这是**唯一**允许整体替换的场景，因为它本来就是「把 N 份重复内容折叠成 1 份」，
  替换是目的本身，不是副作用。

还有一个反向校验：**update 的目标必须已经存在**。

```go
if in.Action == ActionUpdate && !fileExists(target) {
    return false  // 保留源文件，下轮重试
}
```

清单可能过期（文件被用户删了），或者模型在编。这里选择"失败并保留"而不是
"退化成 create"——静默地把 update 变成 create 会掩盖一个真实的不一致。

**模型输出不能指挥删除任意文件**

```go
for _, victim := range in.DeleteFiles {
    if abs, ok := resolveMemoryFile(projectRoot, victim); ok && abs != survivor && fileExists(abs) {
        _ = os.Remove(abs)
    }
}
```

三重过滤：必须是**裸文件名**（`resolveMemoryFile` 拒绝含 `/`、`\`、`..` 的名字，
这一层是**模型输出与文件系统之间的边界**，不能靠信任）、
必须已存在、不能是幸存文件本身。

以及先写后删的顺序：**幸存文件写成功之后**才删被合并的文件。
写失败就一步都不删。

**一任务一动作**

```go
if seen[src] { continue }  // 先到先得
```

模型偶尔会对同一个 task 文件输出两条动作（尤其 create + update）。
不挡住的话，同一个源文件会被删两次，或者被写进两个长期记忆。

**解析失败绝不删源**

```go
if len(actions) == 0 {
    c.logf("[task-consolidate] no usable actions, keeping %d file(s)", len(pending))
    return 0
}
```

这一条最重要。解析失败时如果"顺手清理一下"，就会把**某个真实教训的唯一记录**删掉，
而这个子系统存在的全部意义就是保住那条记录。宁可堆着。

**「体积不单调增长」是结构性保证**

- task 记忆**只减不增**：蒸馏成功即删源，失败即留待下轮（总数单调不增）；
- 长期记忆只经 update（追加，有上限）/ merge（去重）/ skip（丢弃），
  三者都不会让同一份教训被记两遍。

**为什么不设归档目录**

任务书里写了取舍：不设。归档只是把「单调增长」挪到另一个地方，
阶段一不需要审计回溯（要回溯时 `git log` 里有的是）。

**输入控 token**

```go
const MaxConsolidationInputBytes = 48 * 1024
```

超出的部分等下一轮。而且排序是**新的优先**：

```go
sort.Slice(entries, func(i, j int) bool { return entries[i].Name() > entries[j].Name() })
```

配合字节上限，砍掉的是**最旧**的。这是对的取舍方向：最新的教训才和手上的活相关。

**堆积兜底（20 条）**

```go
if len(pending) > MaxPendingTaskMemories {
    c.NotifyActivity()  // 重臂，不是递归
}
```

这里刻意**不递归调用 Run**：此刻还持有 `inFlightMu`，直接递归会撞上自己的 `TryLock`
然后立刻返回，是个空操作（虽然不是 bug，但读代码的人会困惑）。重臂定时器表达的是同一件事。

### 1.7 `internal/agents/subagent.go`（改，钩子挂载点）

任务书指定挂在 `taskMgr.SetCompleted(taskID, output)` 之后。

**为什么不直接 import memory**

`internal/agents` 被 `internal/memory/extractor` 依赖，而 extractor 又依赖 agents。
在这里 import memory 会形成 `agents → memory → (extractor) → agents` 的环。

所以钩子声明为一个裸函数字段：

```go
type TaskManager struct {
    // ...
    OnCompleted func(taskName, output string)
}
```

装配侧（tui / remote）把它连到 `memory.TaskWriter`。这是依赖倒置：
agents 只知道"任务完成时有个回调"，不知道记忆系统存在。

**SetCompleted 的顺序是刻意的**

```go
func (tm *TaskManager) SetCompleted(id, output string) {
    tm.mu.Lock()
    var name string
    if t, ok := tm.tasks[id]; ok {
        t.Status = TaskCompleted
        t.Output = output
        t.DoneAt = time.Now()
        name = t.Name
        tm.notifications = append(tm.notifications, ...)
    }
    hook := tm.OnCompleted
    tm.mu.Unlock()          // ← 先释放锁

    if hook != nil && name != "" {
        go hook(name, output)   // ← 再脱离式执行
    }
}
```

两件事：**状态和通知在锁内提交，钩子在锁外跑**。

如果钩子在锁内跑，一次 60 秒的提取调用会把 `TaskManager` 的锁按住 60 秒——
而主循环下一轮要 `DrainNotifications()`，直接卡死。任务书里"SetCompleted 先行，
提取+写文件异步"这句，落点就是这个 `Unlock()` 的位置。

`go hook(...)` 那行还保证了提取期间持有的 `subCtx` 无关：钩子拿的是
`context.Background()`（在 tui 侧传入），子任务取消不会连带取消记忆写入——
记忆写一半被取消，比写慢一点更糟。

### 1.8 `internal/tui/tui.go` 与 `internal/remote/server.go`（改，装配）

两侧接法完全对称，因为**行为不一致是 bug 而不是 feature**：TUI 里有任务记忆、
headless 会话里没有，这本身就是一种难以排查的不一致。

```go
m.taskMgr.OnCompleted = func(taskName, output string) {
    m.taskWriter.OnSubTaskComplete(context.Background(), taskName, output)
}
```

**`memorySideQuery` 为什么每次现造 client**

抄 `prefetchRelevantMemories` 里 selector 的写法：旁路查询必须有自己的 system prompt，
绝不能改主会话的 system prompt。`llm.NewClient(provider, sysPrompt)` 天然满足这点——
`SetSystemPrompt` 是接口的一部分，每次新建一个 client 就不会有串味风险。

**超时不对称**

- 提取：60 秒
- 蒸馏：120 秒

理由写在代码注释里：蒸馏会改写长期记忆，安静期越长，用户越可能真的走开了，
这时候慢一点没关系。

**usage 的填充在这里**

```go
case llm.StreamEnd:
    usage.InputTokens = e.Usage.InputTokens + e.Usage.CacheReadTokens + e.Usage.CacheCreationTokens
```

`StreamEnd` 携带 `UsageInfo`。注意 Anthropic 的 `cache_read_input_tokens`
不计入 `InputTokens`，所以要手工加上，否则真实 prompt 大小会被低估一大截。

这是 1.5 里说的那个"解耦代价"：memory 包自己拿不到 usage，靠调用方填。
好处是 memory 包测试完全不依赖 llm；代价是这里漏填就是静默的 0。
`errs` 通道用非阻塞 select 读，避免在 TUI goroutine 上 stall。

**Ctrl/C 时停掉定时器**

```go
m.taskConsolidator.Stop()
```

在 `tea.Quit` 之前。在飞的那一轮**不取消**——它只持有一次 LLM 调用，
半路杀掉比让它跑完更糟；它处理的 task 文件留在 `tasks/` 下轮再蒸（任务书风险表已认这条）。

## 2. 设计哲学（可以拿去面试讲的）

1. **暂存态 + 蒸馏，而不是只有一层。**
   task 记忆是会过期的。直接把它当长期记忆存，记忆库就会被"某次任务的临时麻烦"污染，
   而且只能增长不能收缩。做成暂存态 + 空闲蒸馏，规模就被结构性地框住了。

2. **黑名单对模型，白名单对系统。**
   模型写记忆靠黑名单就够了（列清楚别存什么）；系统提取教训必须用白名单
   （只允许这四样，其余一律不存）。黑名单挡不住"动作流水账"这种新形态。

3. **白名单只有一份定义。**
   `WhatNotToSaveTaskSection` 被系统提示词内嵌，不存在"文档写的"和"模型看到的"两份规则。

4. **记忆是增强，不是依赖。**
   全链路静默失败。代价模型是清楚的：少一条记忆 = 下次多踩一次坑；
   记忆子系统出错 = 用户丢当前对话。选后者不可接受。

5. **模型不能指挥文件系统的任意写入/删除。**
   蒸馏器的每个输出字段都过一遍 containment 检查；merge 的删除列表只认裸文件名、
   只认已存在、且必须在幸存文件写成功之后。

6. **先落盘再删源，解析失败一律保留。**
   这条子系统唯一不可让步的性质：**绝不因为处理失败而销毁教训**。

7. **并发用 TryLock，不用 bool 标志位。**
   后者的 check-then-set 不是原子的。

## 3. 踩坑记录

### 3.1 Go 原始字符串里不能直接写 Markdown 反引号

在 `const X = \`...\`` 里写 `` `task` `` 会让编译器提前闭合字符串：

```
memory_types.go:67:81: syntax error: unexpected name task after top level declaration
```

修法：改成 `type: task`（不带反引号）或 `(type: task)`。**字符串字面量里写文档，
要意识到文档本身可能含定界符。**

### 3.2 `path.Join` 的签名是二元的

写 `filepath.Join(GetTaskMemPath(""), name, true)` 这种三参数的会编译失败。
调试中途还短暂把 `resolveLongTermTargetChecked` 的返回值写成了
`filepath.Join(...), name, true` 这种把逗号当返回分隔符的形态——
**先让编译器过一遍，再继续改逻辑**，否则错误会互相掩盖。

### 3.3 一次 Edit 把文件写坏了（5549 行）

改动 `taskExtractionResponse` 结构体时，一次 Edit 意外生成了数千行重复的
`// WorthSaving bool ...` 注释，并且破坏了字段名（`json:"pitfall"` → `json:"pitch"`），
文件从 296 行涨到 5549 行。

处理方式：用 `sed -i '' '166,5428d'` 删掉损坏区间，再检查残留的三行字段，
最后用 Edit 补回正确结构体。`gofmt` 和 `go build` 各跑一遍确认。

**教训**：改一个结构体时优先整块替换而不是逐字段 Edit；
文件行数异常增长（296 → 5549）是很明显的信号，要立刻停下来查，而不是继续编辑。

### 3.4 `remote.installMemExtractor` 是自由函数，拿不到 receiver

它的签名里没有 `*Server`，我在里面写 `s.taskConsolidator.NotifyActivity()` 直接编译失败。

修法：给函数加一个 `consolidator *memory.Consolidator` 参数，
并且调整装配顺序（**先 `installTaskMemory` 再 `installMemExtractor`**，这是真实依赖不是美观问题）。

### 3.5 TUI 里没有 debugLogger 字段

想接日志时写了 `m.debugLogger`，编译报错。项目现有的约定是
`os.Getenv("TENCODER_LLM_DEBUG")` 门控（`internal/llm/openai_compat.go:45` 就是这么干的），
于是加了 `memoryDebugf` 写 **stderr** 而不是 TUI 渲染路径——
往 Bubble Tea 的视图里打日志会破坏布局。

### 3.6 既有测试失败（与本阶段无关，但必须说清）

`go test ./internal/...` 的失败清单：

| 包 | 症状 | 归属 |
|---|---|---|
| `internal/tools` | `package tencoder/internal/media is not in std` | 既有：`internal/media` 包缺失 |
| `internal/config` | `undefined: MediaProviderConfig` 等 | 既有：配置项未实现 |

## 6. 给阶段二的接口

阶段二（子任务检查点 + 独立反思节点）要对接两处：

1. **2.4 偏移事件写入短期任务记忆** —— 直接复用 1.2 的落盘入口。

   阶段五的路由（`internal/llm/router.go`）应当以这套 usage 埋点为数据来源，
   字段已经是对齐的（档位 + 输入/输出 token + 耗时）。
