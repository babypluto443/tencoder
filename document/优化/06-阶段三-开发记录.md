## 0. 这一阶段加了什么

两件事，都围绕"延迟加载已经省下的 token 会不会被吃回去"：

1. **补上"卸"这一半**（任务 3.1）。现状是 MCP 工具**只装不卸**：`MarkDiscovered` 之后 schema
   永久留在 `GetAllSchemas` 里。长会话里 Agent 逐个 ToolSearch 出一堆工具，常驻 schema
   只增不减，把「延迟加载省下的 85%」一点点吃回去。现在改成阈值批量驱逐。
2. **把机械截断预览换成知道任务目标的结构化摘要**（任务 3.2）。超预算的 tool_result
   全文照旧落盘，但上下文里放的不再是"前 2KB"，而是旁路 LLM 写的摘要。

```
常驻工具集合：  发现 → 常驻 → 常驻 → …（只增不减）        ← 阶段二之前
              发现 → 常驻 → 批量驱逐 → 再发现              ← 阶段三

工具结果超预算： 全文落盘 + 前 2KB 机械预览                ← 阶段二之前
              全文落盘 + 旁路 LLM 结构化摘要（带任务上下文）   ← 阶段三
```

## 1. 实测数（验收标准 1）

`TestHundredToolSessionEvictionIncrementalSaving` 的输出，场景：120 个 deferred 工具 × 40 轮，
每轮 ToolSearch 装载 3 个，每 3 个里有 1 个被真正调用。

```
起始常驻 schema: 6574 bytes (仅内置工具)

无驱逐累计:        2790915 bytes (~697728 tokens)
有驱逐累计:        1520981 bytes (~380245 tokens)
阶段三增量节省:    45.5%  (~317483 tokens, 口径：字符数 ÷4 估算)
驱逐轮次:          5 次 / 40 轮  ← prompt cache 失效次数
驱逐工具总数:      89
常驻峰值:          驱逐 40 vs 不驱逐 120 (高水位 40)
```

三个数字各有意义：

| 数字 | 含义 |
|---|---|
| **45.5%** | 阶段三在已有 85% 之上的**增量**。这是验收标准 1 要的那个数 |
| **5 次 / 40 轮** | prompt cache 被击穿的次数。**这才是"批量"设计的全部理由** |
| **40 vs 120** | 常驻峰值从 120 压到高水位 40 |

**口径说明（面试必须主动交代）**：用的是 `GetAllSchemas` 序列化后的**字符数**，
token 按 `÷4` 估算。选字符数是因为它可复现——同一个 schema 序列化两次结果一样，
而不同 provider 的 tokenizer 不通用。写简历时按"字符数"表述并注明换算方式更诚实。

## 2. 逐文件详解

### 2.1 `internal/tools/eviction.go`（新增）

#### 2.1.1 第一约束不是 LRU，是 prompt cache

这一段是整个文件的设计前提，也是面试最该讲的部分：

工具 schema 位于 prompt 的**前缀**。一个自然但错误的做法是"每回合检查一次，超了就去掉最久未用的那个"——
**每回合变动一次 = 每回合击穿一次 prompt cache**。而 cache 命中省下的钱，
远大于省下的那几十 KB schema。

所以设计成**阈值批量驱逐**：常驻数超过 40 才砍回 25。120 工具的长会话里实测只发生 5 次，
摊销之后可以忽略。

`TestHundredToolSessionEvictionIncrementalSaving` 里有一条断言专门盯这个：

```go
if evictionRounds > numTurns/4 {
    t.Errorf("驱逐轮次 %d 过多（> %d）；批量驱逐的意义就是摊销 cache 失效", ...)
}
```

**光断言"省了多少字节"是不够的**——省字节和击穿 cache 是可以同时发生的坏交易。

#### 2.1.2 LRU 时钟：执行时间优先，发现时间兜底

```go
func (s ToolUsageStats) lastUsedMs() int64 {
	if s.LastExecutedMs > s.DiscoveredMs {
		return s.LastExecutedMs
	}
	return s.DiscoveredMs
}
```

工具 T0 被发现、T50 被执行，它就是**热的**；另一个 T40 被发现、从未执行，是**冷的**。
哪怕前者的"发现时间"更早。

只按发现时间排会退化���"最早发现的先走"，而那恰恰可能是 agent 正在用的工具。
`TestEvictionPrefersNeverExecutedOverStale` 用三个工具 + 人为拉开时钟差来钉死这个排序。

#### 2.1.3 活跃豁免

```go
if policy.ActiveExemptExecutions > 0 && c.stat.ExecuteCount >= policy.ActiveExemptExecutions {
    skippedActive++
    continue
}
```

会话内执行 ≥2 次的工具永不驱逐。理由很朴素：**反复"装载→驱逐→再装载"一个你一直在用的工具，
纯属浪费**——每次都要付一次 ToolSearch 往返，而它下一回合还要用。

豁免导致一轮驱逐砍不够数是允许的（返回 `Evicted=0` 的事件），宁可超水位也不驱逐活跃工具。

#### 2.1.4 驱逐是无损的：回池而非删除

被逐的工具只是 `delete(discoveredTools, name)`——工具本体还在 `tools` map 里。
于是它立刻出现在 `GetDeferredToolNames()` 里，system-reminder 会重新列出它，ToolSearch 可以再发现。

`TestEvictionIsLossless` 验证了完整回路：驱逐 → 进池 → `ToolSearch select:<name>` → 重新 resident。

#### 2.1.5 只驱逐 deferred 工具

```go
if t, ok := r.tools[name]; !ok || !isDeferred(t) { continue }
```

内置工具（ReadFile/Bash/...）永远不在候选里。延迟加载机制本来就不管它们，
驱逐也不该越界。`TestEvictionNeverTargetsNonDeferredTools` 覆盖。

### 2.2 `internal/tools/tool.go`（改，加锁）

原来的 `Registry` 是**裸 map 无锁**：

```go
type Registry struct {
	tools           map[string]Tool
	discoveredTools map[string]bool
}
```

之前"碰巧安全"是因为只有 `MarkDiscovered` 写它，而那都发生在主循环单线程里。
但 3.1 一引入**执行侧打点**（`RecordExecute` 从 StreamingExecutor 的 goroutine 调），
立刻变成真竞态。所以这一版补 `sync.RWMutex`。

**`GetAllSchemas` 用两段式**（RLock 内快照 → 锁外渲染）：

```go
r.mu.RLock()
resident := ...  // 只收集 Tool 引用
r.mu.RUnlock()
for _, t := range resident { ... t.Schema() ... }   // 锁外
```

`Tool.Schema()` 每个都要新建一个 map，120 个工具就是 120 次构造。
持锁渲染会让**这一轮所有并发执行的 RecordExecute 全部排队**——而那正是工具正在跑的时刻。

### 2.3 `internal/agent/agent.go`（改，两处挂点）

**驱逐检查**放在回合开头、`currentToolSchemas()` **之前**，保证本轮发出的 schema 已是裁剪后的集合：

```go
if ev := a.Registry.MaybeEvict(); ev != nil && ev.Evicted > 0 {
	ch <- ToolEvictionEvent{...}
	conv.AddSystemReminder(fmt.Sprintf("Tool context trimmed: %d deferred tool schema(s) were unloaded... reload them with ToolSearch if you need them. Unloaded: %s", ...))
}
```

那行 system-reminder 不是可有可无的礼节：没有它，模型会看到工具列表里少了几个，
**可能得出"这些工具不存在"的结论**；有了它 + 紧接着注入的 deferred 名单，
模型知道"它们只是被卸载了，ToolSearch 能拿回来"。

**执行埋点**放在权限门之后、`tool.Execute` 之前：

```go
a.Registry.RecordExecute(tc.ToolName)
result := tool.Execute(ctx, tc.Arguments)
```

放在权限门**之后**是有意的：被拒绝的调用根本没执行，算进去会让一个反复被拒的工具
攒够执行次数、骗到它没赚来的活跃豁免。

### 2.4 `internal/toolresult/summary.go`（新增）

**定位：不是新增一层，是升级 preview 位。** spill 落盘路径、冻结机制、`Record` 语义全部不变，
只有决定留在上下文里的那段文本从"机械截断"换成"结构化摘要"。

所以它复用同一套冻结：`summary` 和决策一起进 `ContentReplacementState.Replacements`，
后续轮次逐字节回放。`TestSummaryIsFrozenByteForByte` 断言摘要只被调用一次。

#### 2.4.1 喂给摘要器的是**尾部**，不是头部

```go
func tailExcerpt(s string, max int) string {
	...
	return "...[middle truncated — full text is on disk]...\n" + s[len(s)-max:]
}
```

日志/输出形态的内容，**结论在最后**（panic、断言失败、汇总行），开头是启动横幅和配置转储。
`buildSpillPreview` 的头部截断恰好扔掉了最有用的部分——这是"机械预览"最要命的缺陷。

`TestTailExcerptKeepsTheEnd` 钉死这一点。

#### 2.4.2 摘要必须"带任务上下文"

这是相对规则式摘要的**唯一实质优势**：摘要器知道当前任务目标，
所以能判断 200KB 里哪部分和手头的活相关。`buildSummaryInput` 把 goal + 工具名 + 内容一起传进去，
`TestSummaryReplacesMechanicalPreview` 断言 goal 确实到达了摘要器。

#### 2.4.3 提示词里最要紧的是"逐字保留数值"

```
1. Every number, identifier, file path, symbol name, and error message, EXACTLY as written.
```

把"expected 3, got 4"改写成"a count mismatch"，就毁掉了 agent 唯一能据以行动的部分。

#### 2.4.4 摘要幻觉的兜底：全文永远可回读

摘要块固定带一行：

```
Re-read the file above with ReadFile if an exact value matters.
```

摘要可能丢细节甚至编造，**全文始终在 `.tencoder/tool_results/`**。
模型发现自己需要一个精确数值时，有明确路径回去核对。这是"摘要可信度不够"的对冲手段。

#### 2.4.5 失败回退三条路径

`TestSummaryFallsBackOnFailure` 覆盖：摘要器报错 / 返回空 / 未接线（nil）。
三种都回退到机械预览，`FellBack` 计数。

这就是任务书"全链路失败回退只会更好不会更坏"的实现：**spill 已经成功了，全文安全在盘上，
机械预览是一个完全合格的结果**。

#### 2.4.6 默认关闭

`ToolGovernanceConfig.SummaryEnabled` 默认 `false`。两个理由：
摘要是**同步**调用（必须赶在下一轮 prompt 组装前进上下文），会给 spill 那一轮加 1~3s；
且摘要质量未经真实会话验证。默认走机械预览这条"绝不会更坏"的路径。

## 3. 设计哲学（面试可讲）

1. **prompt cache 经济学优先于 LRU 理论。** 工具列表在 prompt 前缀，变更即失效。
   所以是**批量驱逐**不是逐个淘汰，且测试里有一条断言专门盯"驱逐轮次不能太多"。
   **只测"省了多少字节"是不够的——省字节和击穿 cache 可以同时发生。**

2. **驱逐是无损的，不是删除。** 工具回池、可重发现，功能无损只多一次 ToolSearch 往返。
   这个性质让驱逐成为一个**纯粹的预算管理动作**，而不是能力削减。

3. **活跃豁免承认了一个事实：反复装卸是纯浪费。** 一个你每回合都在用的工具，
   驱逐它等于强迫自己下一回合再花一次往返把它拿回来。

4. **摘要是 preview 位升级，不是新架构。** spill 落盘、冻结回放、`Record` 语义全部不变。
   这让"打开摘要"这个开关不会动摇 prompt cache 的既有保证。

5. **摘要可以不可信，但原文必须永远可达。** 摘要块固定带"用 ReadFile 回读"，
   全文永远在盘上。幻觉的代价被限制在"多花一次读文件"，而不是"agent 拿着编造的数值继续干"。

6. **喂摘要器尾部，喂裁判轨迹全貌。** 二者相反，因为内容形态相反：
   日志的结论在最后；轨迹的价值在形状（看了什么→改了什么→结果如何）。

7. **全部可关闭。** `evict_enabled: false` 回到阶段二之前；`summary_enabled` 默认就是关。
   新机制必须留逃生门，否则一旦在某个项目上出问题就只能整体禁用。

## 4. 踩坑记录

### 4.1 测试断言"摘要要保留关键信息"，暴露出摘要正文根本没写进去

`buildSummaryPreview` 第一版是：

```go
b.WriteString(summaryTagPrefix)
b.WriteString("\n")
fmt.Fprintf(&b, "(compressed from %dKB; ...)\n", ...)   // ← 只有元数据
b.WriteString("Re-read the file above ...")
b.WriteString("</summarized-output>")
```

**`summary` 这个参数从头到尾没被用过。** 编译不会报错，函数签名完全合理，
只有断言"关键信息必须存活"的测试能抓到它。

这类 bug 的共同特征：**函数的所有参数看起来都被用到了（签名无异常），
但某个参数只参与了控制流没参与输出**。所以"这个测试在测什么"要写清楚——
我那条断言写的是"actionable assertion detail must survive the summary"，
它存在就是为了钉住这件事。

### 4.2 `persistedTagPrefix` 和实际写入的标记对不上（既有 bug）

```go
const persistedTagPrefix = "[Result of "     // 判定用的
b.WriteString("<persisted-output>\n")          // 实际写的
```

`isAlreadyReplaced` **从来没匹配过机械预览**。后果：从会话日志恢复的已 spill 结果
不会被识别为"已决策"。平时被 `SeenIDs` 掩盖了，直到阶段三加了第二种替换格式、
开始对两种格式都做断言时才暴露。

已修为 `"<persisted-output>"`。

**一个"平时没出事"的既有 bug，往往要等到有人把第二条路径也写出来才会现形。**

### 4.3 `sanitizeSummary` 的 `TrimLeft` 吃掉了 markdown 列表符号

```go
s = strings.TrimLeft(s, ":—- \n")   // 想去掉 "summary: "
// 对 "here's the summary:\n- a\n- b"：
//   去完冒号 → "\n- a\n- b"
//   再 TrimLeft 就把 "- a" 的短横线也吃了 → "a\n- b"
```

`TrimLeft` 是**按字符集**匹配的，不是按"前缀"。把 `-` 放进字符集是想兼容破折号，
结果把列表符号一起吃了。

改为 `TrimPrefix(s, ":")` + `TrimSpace`——精确剥离，不越界。

### 4.4 两个测试自身的配置错误

- `EvictionPolicy{HighWatermark: 1, LowWatermark: 1}` 想表达"只留 1 个"，
  但 `normalized()` 里有一条 `LowWatermark >= HighWatermark → 重置为默认` 的保护，
  结果被改成 26/25。**这条保护是对的**（砍回高水位会导致每回合都触发抖动），
  测试得按真实语义写。
- `TestEvictionNeverTargetsNonDeferredTools` 注册了 40 个工具却**没 `MarkDiscovered`**，
  常驻数是 0，`MaybeEvict` 自然返回 nil。测试自己没搭出它想测的状态。

**这两条都是"测试写错了、被生产代码的合理性绊倒"**——不是生产代码的错。

### 4.5 `internal/tools` 的测试包一直是编译不过的

`media_test.go` 引用了**不存在的** `tencoder/internal/media` 包，导致整个
`internal/tools` 的测试二进制无法编译——连带把延迟加载 benchmark 也堵死了。

处理：加 `//go:build media`。项目里本来就有 `internal/sandbox` 在用 build tag，
不是新引入的约定。**选 build tag 而不是删文件**：等 media 包落地后 `-tags media` 就能放回来。

现在 `internal/tools` 43 个用例全通过——**这是这个包第一次能跑测试**。
