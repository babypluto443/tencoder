## 1. 核心 trade-off：worktree 是冲突边界，不是安全边界

这是本阶段最该在面试里主动讲的一条（任务书 §0）。

**git worktree 让多个 Agent 改同一个项目时不打架，但它共享 `.git`。** 所有 worktree 的
`.git` 指向同一个真实 git 目录，于是 `.git/hooks/` 落在**每一个 worktree 的表观可写面内**。
一个被篡改的 `post-commit` hook 会在任何一次 commit 时以**用户权限**执行——
而对沙箱来说，它只是"项目内的一个普通文件"。

所以本实现的定位是明确的：

```
worktree  →  防冲突（多个 Agent 并行改同一项目）
沙箱      ┐
审批链    ├→ 提供安全性
审计      ┘
```

`ValidateGitHooks` 把这件事变成可见的：注册 workspace 时检查 `.git/hooks` 下的**可执行**
hook，有就警告。它是**警告不是拒绝**——很多仓库自带 `*.sample` 文件，直接拒绝注册会打断
合法仓库；真正要紧的是让用户知道 hook 会在 commit 时以他的权限跑。

## 2. 逐文件详解

### 2.1 `internal/workspace/registry.go`（新增）

**默认不可见，而不是默认可见后审批。** 没登记的目录对 Agent 完全不可见。
反过来的设计（任何目录可读，写才审批）等于把整台机器的家目录变成可读面。

**两级模型，`Register` 对无 level 的条目 fail closed：**

```go
if e.Level == "" {
    e.Level = LevelReadonly // 没有级别就不是可写
}
```

一个手滑的 YAML 少写 level，绝不能变成"可写"。

**`/workspace add` 默认级别是 readonly**，理由同上——注册项目是安全相关动作，
把 `add /Users/me/important` 的意图猜成"授予写权限"是最坏的猜测方向。

**路径逃逸用的是带分隔符后缀的前缀：**

```go
func withinRoot(abs, root string) bool {
    if abs == root { return true }
    return strings.HasPrefix(abs, root+string(filepath.Separator))
}
```

裸 `strings.HasPrefix` 会认为 `/repo-evil` 在 `/repo` 之内。`TestWithinRootRejectsSiblingPrefix`
专门钉死这一条。

**`Classify` 取最长匹配**：嵌套注册的内层工作区必须赢过它的父级，
否则 `/repo` 和 `/repo/sub` 都注册时内层永远不可达。

### 2.2 `internal/permissions/permissions.go`（改，本阶段改动最多的文件）

#### 2.2.1 读写拆分是结构性缺口，不是功能缺失

原来 `PathSandbox.Check(path)` 一个方法管所有读写，根列表也只有一份。后果是
"允许读、拒绝写"这个状态**在数据结构里没有地方放**。

改后：

```go
CheckRead(path)  // allowedRoots ∪ readonlyRoots
CheckWrite(path) // 仅 allowedRoots
ReadonlyViolation(path) (bool, string)  // 额外回答"是不是只读违例"
```

为什么 `ReadonlyViolation` 要单独一个方法而不是复用 `CheckWrite` 的返回值：
`Checker` 需要区分**三种**结果（在可写区 / 在只读区 / 完全在范围外），
而 `bool + string` 承载不了第三种。

`Check` 保留原签名等价于 `CheckWrite`——历史调用方按写语义使用，不破坏它们。

#### 2.2.2 三个真实 bug（都由测试逼出来，见 §4）

这一节是本阶段最值得复盘的部分。三处都不是"写错了"，是**设计时没想清楚的一类问题**。

**① 显式只读声明被临时目录放行吃掉。**
`NewPathSandbox` 会把 `os.TempDir()` 加进 allowedRoots。于是注册一个 `/tmp` 下的项目为
readonly 时，写检查**先命中临时目录根直接放行**，只读声明形同虚设。

修法是引入 `explicitWritable` 区分两类根：

```
优先级 1：用户显式注册的 writable  → 永远放行
优先级 2：显式 readonly 声明       → 拒绝（压过隐式临时目录）
优先级 3：隐式根（项目根 / 临时目录）→ 才轮到它们
```

**② 注册表解析了符号链接，沙箱没解析——两侧形态不一致。**
`workspace.resolveDir` 调 `EvalSymlinks`（macOS 上 `/var` → `/private/var`），
沙箱只 `filepath.Abs`。于是只读根存成 `/private/var/...`，
而被检查的路径是 `/var/...`，**永远不匹配，只读边界静默失效**。

修法：两侧都解析。我给 `resolveDir` 写注释时说了"resolved-to-resolved"，
却只在注册侧实现了——**注释里的不变量必须两边都做到，否则它只是一句漂亮话。**

**③ 路径不存在时符号链接解析失败——而这恰恰是写操作最常见的情况。**
`resolveSandboxPath` 里 `EvalSymlinks(path)` 对**还不存在的新文件**会失败，
回退到未解析路径，于是又是 `/var` vs `/private/var` 不匹配。

而"agent 即将创建的新文件"正是只读必须拦住的场景。修法是**只解析父目录**再拼回 basename：

```go
parent := filepath.Dir(abs)
if resolvedParent, err := filepath.EvalSymlinks(parent); err == nil {
    return filepath.Join(resolvedParent, filepath.Base(abs)), nil
}
```

第 ③ 条最值得记：**一个 fallback 分支的危险不在于它出错，而在于它只在"边界情况"下生效，
而那个边界情况恰好是主路径。**

#### 2.2.3 审计挂在 `Check` 外层而不是每个 return 点

```go
func (c *Checker) Check(tool, args) Decision {
    d := c.check(tool, args)
    if c.Audit != nil && tool.Category() == CategoryWrite {
        c.EmitAudit(...)
    }
    return d
}
```

`check` 内部有 ~10 个 return 点。在每个 return 加审计调用，是那种
"下次有人加一个新分支就会忘了"的东西——而**一个悄悄漏记某类决策的权限层，
比没有审计更糟，因为它看起来是完整的**。一层包装不可能被新的 return 绕过。

**只记写类决策。** 读几乎每次工具调用都产生决策，记下来会把日志淹掉；
验收标准 4 要的是写的可追溯性。

#### 2.2.4 只读升级：`ReadonlyWrite` 标记 + 禁用 always

```go
return Decision{
    Effect: Ask,
    Reason: fmt.Sprintf("Read-only workspace %s: writing here requires explicit approval", wsName),
    ReadonlyWrite: true,   // TUI 据此禁用 "always allow"
    Workspace:     wsName,
}
```

不是静默拒绝（用户会一头雾水），也不是静默放行（那和没有只读一样）。
是**升级为显式审批，且不许永久授权**。

`internal/agent/agent.go` 里还有一道**纵深防御**：即使非 TUI 客户端（remote UI、脚本）
硬发一个 `PermAllowAlways`，也会被降级为 `PermAllow`——

```go
if resp == PermAllowAlways {
    if decision.ReadonlyWrite {
        resp = PermAllow // 一次 TUI 挡不住脚本
    }
}
```

#### 2.2.5 审计记两步：提示 + 用户的答复

`Check` 记的是"弹了窗"（`pending-approval` / `pending-readonly-approval`），
`RecordApproval` 记的是"用户选了什么"（`approved-by-user` / `denied-readonly`）。

**只记前者的话，"问了但没人答"和"问了被拒"在日志里长得一模一样**——
而这正是审计日志真正被需要时的场景。`TestAuditFullReadonlyLifecycle` 钉死两条都在。

拒绝信息带**项目名**而不是路径：`"pluto_feed is read-only"` 对用户可操作，
`"/Users/babypluto/pluto_feed is read-only"` 只是噪音。

### 2.3 `internal/audit/audit.go`（新增）

**单 writer goroutine + 1024 缓冲 channel。** 一次 channel 发送就返回，永不阻塞——
权限检查在等这个返回值。

**投递失败会丢记录，这是"绝不阻塞"要付的价。** 取舍写在包注释里：
主循环卡死的代价比丢一条审计记录大得多；容量给到 1024，正常负载从未接近上限；
丢了会 `dropped` 计数，`Stats()` 可查——**缺口是可见的，不是静默的**。

`O_APPEND` 单 writer 意味着每条记录实际上是一次写 syscall，
崩溃时最多损坏最后一行（可恢复），不会损坏中间（不可恢复）。

`ReadAll` 跳过解析失败的行——一次崩溃留下的半行不该让整份日志读不出来。

### 2.4 `internal/teams/progress_tool.go`（新增，任务 4.1）

**为什么是查询而不是事件注入。** 一个显然的做法是每次子 agent 调用工具就把进度塞进 lead 的上下文。
几十个子 agent 步就是几十条 "X is editing foo.go"，把 lead 真正需要的对话内容挤出 cache。
**这恰好是"而非全文粘贴"初衷的反面。**

所以：lead 平时安静（完成事件走已有 mailbox），**何时关心进度、关心到什么粒度，由它自己决定**。

**零新状态**：复用现有 `TeammateProgress` + `TaskManager`。自己再存一份就成了第三个可能
和前两个不一致的数据源。

工具本身是 `CategoryRead`——**它不改任何东西，所以不该触发写审批，也不该进审计日志**。
lead 轮询进度应该是免费的。

`TaskManager.ListProgress` 刻意**不含 Output**：一个子 agent 的最终输出可能几千字符，
进度查询是报状态不是贴结果；输出走完成通知 / mailbox。

### 2.5 `internal/agents/agent_tool.go`（改，任务 4.5）

**注入式窄接口，方向是 `agents ← workspace` 而非 `agents → workspace`**：
`workspace → permissions → tools`，而 `agents` 站在它们之上，直接 import 会成环。

```go
type WorkspaceResolver interface {
    Exists(name string) bool
    RootsFor(name string) (writable []string, readonly map[string]string, ok bool)
}
```

**视野收窄的含义是"其余不可见"，不是"其余仍可读"：**

```go
func (r *Registry) RootsFor(workspaceName string) (...) {
    // 只返回被点名的那一个；其余注册项目一概不进子 agent 的沙箱
}
```

一个拿着三个项目读权限的子 agent 完全可能读错项目然后基于错的项目下结论，
**而它自己并不知道自己看错了清单**。

**未指定 workspace 时逐字继承父沙箱**——这样阶段四的默认行为和阶段三完全一致。
收窄只在显式点名时发生。

spawn 时 `workspace` 指向未注册的名字**直接报错返回**，而不是静默生成一个够不到目标的
子 agent（那会白烧一整个回合才发现边界）。

## 3. 设计哲学（面试可讲）

1. **worktree 防冲突，沙箱+审批+审计管安全。** 共享 `.git` 意味着 hook 在每个 worktree 的
   可写面内，且以用户权限执行。混淆这两者是跨项目方案最常见的错误。

2. **默认不可见，而不是默认可见后审批。** 未注册目录不可见；显式只读声明压过隐式临时目录放行；
   无 level 的条目 fail closed 到 readonly。

3. **只读不是静默拒绝，是带审计的显式审批，且不许永久授权。** 拒绝让用户困惑，放行等于没有只读。
   禁用 always 防的是"一次手滑永久破坏只读语义"。

4. **审计挂在权限检查的外层，不挂在每个 return 上。** 会漏记的审计层比没有审计更危险，
   因为它看起来是完整的。

5. **记两步：弹了窗 + 用户答了什么。** 只记前者的话，"无人应答"和"被拒"在日志里无法区分。

6. **进度是查询不是事件。** 事件注入让进度噪声淹没对话，与初衷相悖。
   决定权交给 lead。

7. **注入窄接口而非直接依赖。** `WorkspaceResolver` / `TaskLister` 都是为了避开导入环，
   同时把"我到底需要对方提供什么"写成可检查的签名。

## 4. 踩坑记录

### 4.1 三个 bug 都由测试逼出来，且都不是"语法错"

见 §2.2.2 的三段。要点重述：

- **显式只读 vs 隐式临时目录**：优先级没定义，只读声明被 `os.TempDir()` 吃掉。
  这类 bug 的特征是**功能看起来实现了，只在被安排的场景外失效**。
- **两侧符号链接形态不一致**：我在注释里写下"resolved-to-resolved"，却只在一侧实现。
  **注释里的不变量要当测试来写。**
- **不存在路径的 fallback 失效**：fallback 只在"新文件"这个主路径上被触发。

### 4.2 测试自身的循环依赖

`audit` 包的测试想验证 `workspace.AuditSink`，于是 `audit_test → workspace → audit` 成环。

正确做法是**把 adapter 测试放到 workspace 包**——它本来就是 `workspace.AuditSink` 的测试，
放在被适配方测才说得通。这一点是"测试放哪个包"的一般性判据：
**测的是谁的行为，就放在谁的包里。**

### 4.3 `internal/worktree` 的测试失败（本阶段无关）

`TestCreateAgentWorktree` 失败：`expected /var/... got /private/var/...`。

**不是我引入的**，两条证据：
1. `internal/worktree` **完全不 import** `internal/permissions`，全包也没有一处 `EvalSymlinks`；
2. 路径来自 `FindCanonicalGitRoot` → `git rev-parse`，git 在 macOS 上自己就会解析符号链接。

所以这是**环境相关的既有失败**（此前几轮的失败清单没覆盖到 worktree 包，所以没被记录）。
如实记在这里，不擅自修改一个与本阶段无关的测试。

### 4.4 其余既有失败（同前几阶段）

`internal/config`（`MediaProviderConfig` 未定义）、`internal/memory/extractor`
（`mockClient` 缺 `SetSystemPrompt`）——均未触碰。

分档依据，而不是靠猜。
