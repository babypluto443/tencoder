# 阶段二开发任务：子任务检查点与独立反思节点

> 制定日期：2026-10-16
> 来源：`优化任务书.md` 阶段二 + grill-me 决策会话（4 分支全部闭合）
> 上游文档：`document/优化/优化任务书.md`；依赖：阶段一已落地（TaskWriter / task_consolidate / tasks 召回）
> 预计工期：约 1.5 周
> 目标数字：**目标偏移占比 32% → 11%**（口径见 §4，基线实测）

## 0. 设计总纲（一句话版）

- **反思节点是"第三人称旁路裁判"**：独立上下文、轻量模型、事件驱动——不在主 agent 的上下文里占一个字，却能在偏移高发的四个时刻拦一道。
- **每事件 1 次反思调用；单次 No 轻处置（重申目标），连续 K=3 次 No 重处置（中断重规划）**。K=3 滑动窗口就是"投票防抖"——单次 No 可能是裁判抖，连续 3 次才是真偏移。
- 反思失败/超时**静默跳过**（与记忆子系统同一哲学）：漏拦一次的成本远小于卡死主循环。

## 2. 分支决策记录（grill-me 定案）

### A. 反思调用架构：异步预取

- 工具结果落盘（`conv.AddToolResultsMessage`）后**立刻 fire 反思 goroutine**——此刻"目标 + 最近轨迹"已齐；
- 下一轮迭代开头**限时等待 ≤5s** 消费判定：就绪则按处置链注入；超时则丢弃本次判定（防抖窗口不计），不阻塞主循环；
- 一回合内多事件触发时，**只保留最新判定**（旧判定被覆盖——对当前轨迹的判断以最新为准）；
- 模式与现有 `MemoryRecallCh` prefetch-consume 同构（`agent.go` 已有先例）。

### B. 四个触发事件 → 代码映射

| 简历事件 | 代码映射 | 触发点 |
|---|---|---|
| 定位完成 | 滑动窗口启发式：**连续 ≥3 个只读工具结果**（ReadFile/Glob/Grep/ToolSearch）**后首个写类工具调用成功** | `CollectResults` 后判定窗口 |
| 补丁生成 | `EditFile`/`WriteFile` 工具结果成功返回（`!isError`） | 同上 |
| 测试失败 | 任意工具结果 `isError=true`（Bash 跑测试失败是典型，但不猜语义） | 同上 |
| 异常回调 | `handleStreamError` 的 retry 路径（rate limit / context 超长压缩重试）+ `max_tokens` 恢复 | 主循环异常处理处 |
| （兜底）周期检查 | 配置项 `reflection.periodic`，**默认 false**；开启时每 N 回合强制一次 | 迭代计数处 |

定位完成选启发式窗口的理由：这正是偏移最高发的时刻——定位阶段看错了地方，接下来改的就是错的文件；且不依赖多 agent 拓扑，单 agent 任务也覆盖。

### C. 处置链（对接 2.3）

1. 判定 **No** → `conv.AddSystemReminder` 注入目标重申（含：原始目标一句话 + 本次判定指出的偏离点）；防抖窗口 +1；
2. 窗口内出现 **Yes** → 计数清零；
3. **连续 K=3 次 No** → 中断重规划：注入重规划指令（明确告知"当前路径已连续偏离目标，停止当前做法，重新陈述计划后再动手"），重规划后窗口清零；
4. 重规划触发时（对接 2.4）：调用阶段一 `TaskWriter.OnSubTaskComplete`，把"偏移"当坑提取成任务记忆（taskName 用 `goal-drift: <任务名>`），偏移轨迹摘要作为 output 传入——阶段一管线零改动。

### D. 反思节点输入/输出（对接 2.1）

- **输入**：任务目标（会话首条 user 消息，截断至 ~2KB）+ 最近轨迹摘要（最近 ~10 条 assistant text / tool use / tool result 的压缩视图，截断至 ~8KB）；
- **输出**：严格 JSON `{"on_track": true}` 或 `{"on_track": false, "deviation": "<一句话偏离点>"}`；解析失败视为本次判定无效（不计窗口）；
- **模型**：注入式旁路调用（阶段一 `TaskExtractorFn` 同款接口模式），绑定 **light 档**——阶段五路由的第一个真实客户，2.5 在此预埋。

### E. 偏移率口径与基线（对接验收 1，基线实测）

- **基准场景**：三文件协同还原测试任务（agent 需同时正确修改三个文件）；
- **偏移判定自动化**：每次任务跑完，把最终 diff + 任务目标喂给**旁路强模型**判定调用，输出 per-file 是否覆盖目标改动、有无目标外改动 → 任一文件缺失或存在目标外改动即记偏移；
- **基线**：关反思批跑 ≥10 次实测（数字是多少写多少），开反思再跑 ≥10 次；批跑复用 `tencoder-eval`/`mabench` 基建；
- 简历表述："实测基线 X% → ≤11%（各 ≥10 次取均值）"，批跑日志背书。

## 4. 验收标准（自任务书，口径已定）

1. 上述口径下偏移占比达成 **基线（实测）→ ≤11%**，两组各 ≥10 次取均值，批跑日志可追溯；
2. 反思节点自身 token 开销可见且可控：事件驱动非每步触发；单行日志出"每次触发均摊 token"；
3. 四个触发事件（定位完成/补丁生成/测试失败/异常回调）均有至少一次真实触发记录（开发记录中附日志证据）。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 反思调用拖慢主循环 | 异步预取 + ≤5s 超时丢弃；轻量模型；默认仅事件触发 |
| 启发式窗口误判"定位完成"（误触发） | 误触发只多一次轻量调用；判定 Yes 无副作用；窗口阈值 3 可配置 |
| 反思模型本身误判（真偏移判 Yes） | K=3 防抖只防误报不防漏报——漏报由评测数字兜底暴露；提示词强调"宁可多报 No" |
| 基线批跑成本（20 次强模型任务） | 任务书唯一带数字的验收，不省；场景任务刻意小（三文件）控制单次成本 |
| 重规划中断的用户体验 | 重规划指令明确告知原因与要求；TUI 侧事件流透出"反思判偏移"提示 |
